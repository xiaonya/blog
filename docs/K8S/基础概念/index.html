入门基础概念

这一页记的是 k8s 的基本概念，先有个整体印象，具体操作在各周笔记里。

Kubernetes构成​

图里画的是组件的归属关系和 kubelet 与 apiserver 的通信，kubectl 入口和 CNI 的跨节点网络后面笔记里再讲。

控制平面​

  • kube-apiserver：所有请求的入口，kubectl、各个控制器、kubelet 都通过它读写数据。它本身不存状态，状态在 etcd 里。
  • etcd：集群的状态都存在这里，键值存储，用 Raft 保证一致性。etcd 挂了所有写操作都会失败，已运行的容器不受影响。
  • kube-scheduler：决定 Pod 调度到哪个节点，只做决策，不负责把容器拉起来。
  • kube-controller-manager：里面跑着一堆控制器，Node、ReplicaSet、Deployment、Endpoint 等，作用是把实际状态往期望状态收敛。
  • cloud-controller-manager：对接云厂商的负载均衡、路由这些资源，自建集群一般用不到。

工作节点​

  • kubelet：节点上的主要进程，向 apiserver 注册节点，按 PodSpec 起容器，执行探针，上报节点状态。
  • kube-proxy：维护节点上 Service 的转发规则，iptables 或 ipvs。
  • 容器运行时：真正跑容器的是 containerd，docker 那套 dockershim 新版本已经移除了。

控制平面组件是静态 Pod​

kubeadm 搭的集群里，apiserver、etcd、scheduler、controller-manager 都是 /etc/kubernetes/manifests/ 下的静态 Pod，kubelet 监控这个目录，文件在就拉起，不经过 apiserver。

所以 apiserver 起不来的时候 kubectl 用不了，但 kubelet 还活着，会继续按目录里的文件重建它。排查要看 journalctl -u kubelet，不是 systemctl。改控制平面的参数也是改这个目录里的 yaml，改完 kubelet 自己会重启对应的 Pod。

证书和 kubeconfig​

kubeadm init 生成两样东西：/etc/kubernetes/pki/ 下的一套证书，和 /etc/kubernetes/admin.conf 这个 kubeconfig。CA 证书 10 年，组件证书 1 年。

组件证书不会自动续期，到期 apiserver 这些就起不来了。查剩余时间用 kubeadm certs check-expiration，续期用 kubeadm certs renew all。kubelet 的客户端证书是自动轮换的，不用管。

搭建过程见 集群初始化，组件职责的细节见 集群架构与控制平面组件。

对象的结构​

k8s 里的对象结构都差不多，四段：

  • apiVersion：属于哪个 API 组和版本，比如 v1、apps/v1
  • kind：对象类型，Pod、Deployment、Ingress 等
  • metadata：名字、命名空间、labels、annotations
  • spec：期望状态，自己写的那部分
  • status：实际状态，系统写的

最上面还有一层作用域的区别。Namespace、Node、PV、StorageClass、ClusterRole 这些是集群级的，带不带 -n 都一样；Pod、Service、ConfigMap、Deployment 这些在命名空间里，-n 指定的就是它们。kubectl api-resources 能看清哪些是 namespaced。

查字段用 kubectl explain，比翻文档快：

kubectl api-resources
kubectl api-resources --namespaced=false
kubectl explain pod.spec.containers
kubectl explain deploy.spec --recursive

工作负载​

对象干什么的副本数由谁定
Pod最小的调度单元，一个或多个容器自己定
ReplicaSet保证 N 个副本存在replicas
Deployment管 ReplicaSet，提供滚动更新和回滚replicas
DaemonSet每个可调度节点跑一个节点数
StatefulSet有序、稳定名字、专属存储replicas
Job跑成功 N 次就结束completions
CronJob定时创建 Jobschedule

Deployment 管 ReplicaSet，ReplicaSet 管 Pod，靠 selector 匹配。StatefulSet 多一个 headless Service，Pod 名字是固定的。

网络​

Pod 有自己的 IP，同一个 Pod 里的容器共用一个 network namespace，互相用 localhost 就能通。

Service 是一组 Pod 的固定入口。这里容易误解：ClusterIP 是个虚拟地址，节点上没有进程在监听，ss -tlnp 也查不到 nodePort。真正的转发规则是 kube-proxy 写到每个节点 iptables 里的，它监听 Service 和 EndpointSlice 的变化，把目标地址改写成某个 Pod 的 IP。

Service 的类型：

  • ClusterIP：默认，只在集群内可访问
  • NodePort：每个节点开一个 30000 以上的端口
  • LoadBalancer：需要云厂商支持
  • ExternalName：CNAME 到外部域名
  • Headless：clusterIP 设成 None，直接返回 Pod IP，StatefulSet 用这个

DNS 由 CoreDNS 提供，默认地址 10.96.0.10。完整域名是 service.namespace.svc.cluster.local，同一个命名空间里直接写 service 名字就行。

集群外部访问进来用 Ingress 或 Gateway API，Pod 之间谁能访问谁用 NetworkPolicy。这四块的内容分别在 Week 5 的 Service 与 Endpoints、CoreDNS 与服务发现、Ingress 与 Ingress Controller、NetworkPolicy 网络策略。

存储​

层是什么解决什么
容器可写层容器自己的文件系统容器重建就没了
VolumePod 级别的存储容器重建不丢，Pod 删了还是没
PV / PVC集群级别的存储资源跨 Pod 生命周期，但要手工建 PV
StorageClass存储的模板自动创建 PV，不用手工建

Volume 和 Pod 同生命周期。PV 是集群级资源，PVC 是命名空间里的申请，两者按容量、访问模式匹配绑定。

StorageClass 用 provisioner 动态创建 PV，volumeBindingMode 有两个值：Immediate 是 PVC 一创建就绑定，WaitForFirstConsumer 是等 Pod 调度之后再绑，本地存储一般用后者。allowVolumeExpansion 决定 PVC 能不能扩容。

细节见 PV / PVC 生命周期 和 StorageClass 与动态供给。

ConfigMap 和 Secret​

两个都是往 Pod 里传配置的对象。ConfigMap 存明文，Secret 存 base64。

base64 只是编码不是加密，一条命令就能还原，所以 Secret 的安全靠的是 RBAC，控制谁能 get secret。

用法有两种：注入环境变量，或者挂成 volume。环境变量不会随对象更新，要重启 Pod 才生效；volume 挂载会热更新，用了 subPath 的除外。

资源和调度​

requests 是调度时看的，节点得有这么多空闲资源 Pod 才能被调度上去。limits 是运行时的硬上限。

按这两个字段的组合分三个 QoS 等级：

  • Guaranteed：requests 和 limits 都设了，而且相等
  • Burstable：只设了一部分
  • BestEffort：都没设

节点资源紧张的时候按 BestEffort、Burstable、Guaranteed 的顺序驱逐。

其他影响调度的手段有 nodeSelector、nodeAffinity、podAffinity，节点上的污点用 tolerations 匹配。

学习顺序​

先跟着 Week 0-1 把集群搭起来（基线准备 → 安装前置操作 → 集群初始化），然后按周往下走。概念的细节在各周笔记里，命令忘了就查命令速查。
