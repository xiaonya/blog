# 入门基础概念

这一页是全局地图：先把「有哪些东西、各自管什么」建起来，细节再去各周笔记里看。

## Kubernetes 解决什么问题

手工跑容器有三个绕不过去的问题：容器挂了没人拉起、扩缩容要人工、多台机器之间不知道怎么调度和互联。K8s 的做法是把这些都写成声明式的对象：

- 你提交的是**期望状态**（`spec`），不是一串执行命令
- 控制器不断对比期望状态和**实际状态**（`status`），有差异就收敛
- 收敛过程全部通过 API Server 完成，所有组件都是它的客户端

理解「声明式 + 控制器循环」这两个词，后面所有对象都只是它的不同表现形式。

## Kubernetes 构成

### 控制平面（Control Plane）

| 组件 | 职责 | 坏了会怎样 |
|---|---|---|
| **kube-apiserver** | 唯一入口，所有组件、kubectl、控制器都经它，无状态可水平扩展 | 全集群失去管理面，`kubectl` 全部失败；已运行的 Pod 仍在跑 |
| **etcd** | 集群唯一的状态数据库，键值存储 + Raft 一致性 | 集群「失忆」，所有写操作失败；恢复靠备份快照 |
| **kube-scheduler** | 只做决策：把 Pod 分配到哪个节点，不负责拉起 | 新 Pod 一直 `Pending`，已运行的不受影响 |
| **kube-controller-manager** | 跑一堆控制器（Node / ReplicaSet / Deployment / Endpoint 等），做期望状态收敛 | 副本不再自愈、Service 端点不更新 |
| **cloud-controller-manager** | 与云厂商 API 交互（负载均衡、路由），自建集群通常不部署 | — |

### 工作节点（Worker Node）

| 组件 | 职责 |
|---|---|
| **kubelet** | 节点管家：向 apiserver 注册节点、按 PodSpec 拉起容器、执行探针、上报状态 |
| **kube-proxy** | 在每个节点维护 Service 的转发规则（iptables / ipvs） |
| **容器运行时** | 真正跑容器，实践用 containerd（dockershim 已移除） |

### 一个容易踩的细节：控制平面是静态 Pod

`kubeadm` 部署的控制平面组件不是 systemd 服务，而是 `/etc/kubernetes/manifests/` 下的静态 Pod 清单，由 **kubelet 直接监控该目录**拉起，不经过 apiserver。

推论有两条：

- apiserver 起不来时 `kubectl` 用不了，但 kubelet 还活着，仍会按目录重建它 —— 所以排障要看 `journalctl -u kubelet`，不是 `systemctl status kube-apiserver`
- 想改控制平面组件参数，改 manifests 目录里的 YAML，kubelet 会自动重启对应 Pod

### 证书与 kubeconfig

`kubeadm init` 产出两样关键东西：`/etc/kubernetes/pki/`（一套内部 PKI）和 `/etc/kubernetes/admin.conf`（管理员 kubeconfig）。CA 证书 10 年，组件证书 1 年且**不自动续期**，用 `kubeadm certs check-expiration` 查看、`kubeadm certs renew all` 续期。

详见 [集群初始化 · kubeadm 与 Calico](./CKA/Week0-1/03-集群初始化.md) 与 [集群架构与控制平面组件](./CKA/Week0-1/04-集群架构与控制平面组件.md)。

## API 对象模型

**每个 K8s 对象都是同一套骨架：**

| 字段 | 含义 | 例子 |
|---|---|---|
| `apiVersion` | 属于哪个 API 组和版本 | `v1`、`apps/v1`、`networking.k8s.io/v1` |
| `kind` | 对象类型 | `Pod`、`Deployment`、`Ingress` |
| `metadata` | 身份信息 | `name`、`namespace`、`labels`、`annotations` |
| `spec` | 期望状态（你写的） | 镜像、副本数、端口 |
| `status` | 实际状态（系统写的） | 副本就绪数、Pod IP |

两个作用域要分清：

- **命名空间级**：Pod、Service、ConfigMap、Secret、PVC、Deployment…（受 `-n` 影响）
- **集群级**：Node、PV、StorageClass、ClusterRole、Namespace 本身（不受 `-n` 影响）

查类型和查字段的两个命令，比翻文档快：

```bash
kubectl api-resources                      # 有哪些 kind，是否 namespaced
kubectl api-resources --namespaced=false   # 只看集群级
kubectl explain pod.spec.containers        # 某字段是什么、必填否
kubectl explain deploy.spec --recursive    # 递归展开整棵 schema
```

## 工作负载家族

| 对象 | 一句话 | 副本数由谁定 | 典型场景 |
|---|---|---|---|
| **Pod** | 最小调度单元，一个或多个容器共享网络与存储 | 你自己 | 练习、排障、临时任务 |
| **ReplicaSet** | 保证 N 个 Pod 副本存在 | `replicas` | 一般不直接用，由 Deployment 管理 |
| **Deployment** | 管理 ReplicaSet，提供滚动更新与回滚 | `replicas` | 无状态 Web 服务（最常用） |
| **DaemonSet** | 每个可调度节点跑一个 Pod | 节点数 | CNI、日志采集、监控 agent |
| **StatefulSet** | 有序、稳定网络标识、专属存储 | `replicas` | 数据库、MQ、ZooKeeper |
| **Job** | 跑成功 N 次即结束 | `completions` | 迁移脚本、批处理 |
| **CronJob** | 定时创建 Job | `schedule` | 备份、对账、清理 |

关系主线：`Deployment → ReplicaSet → Pod`，层层由上层控制器的 selector 匹配下层。

## 网络模型

四条独立的主线，别混在一起看：

| 层 | 管什么 | 关键对象 |
|---|---|---|
| Pod 网络 | 每个 Pod 一个 IP，同 Pod 内多容器共享 network namespace，互通用 `localhost` | CNI（Calico） |
| 服务发现与负载均衡 | 给一组 Pod 一个稳定入口 | Service、CoreDNS、EndpointSlice |
| 南北向入口 | 把集群外流量引进来 | Ingress、Gateway API |
| 东西向策略 | Pod 之间谁能访问谁 | NetworkPolicy |

**Service 最容易误解的地方：它不是转发进程，是规则。**

- `ClusterIP` 是虚拟 IP，集群里没有网卡在监听，`ss -tlnp` 也查不到 `nodePort`
- 真正干活的是每个节点上的 `kube-proxy`，它 watch Service/EndpointSlice，在本机写 iptables DNAT 规则，把目标地址改写为某个真实 Pod IP

五种类型：`ClusterIP`（默认，仅集群内）、`NodePort`（每节点开一个 30000-32767 的端口）、`LoadBalancer`（依赖云 LB）、`ExternalName`（CNAME 到外部域名）、`Headless`（`clusterIP: None`，直接返回 Pod IP，StatefulSet 用）。

DNS 由 CoreDNS 提供（默认 `10.96.0.10`），完整域名 `service.namespace.svc.cluster.local`，同命名空间可简写为 `service`。

详见 Week 5 的 [Service 与 Endpoints](./CKA/Week5/01-Service与Endpoints.md)、[CoreDNS 与服务发现](./CKA/Week5/02-CoreDNS与服务发现.md)、[Ingress 与 Ingress Controller](./CKA/Week5/03-Ingress与Controller.md)、[NetworkPolicy 网络策略](./CKA/Week5/04-NetworkPolicy.md)。

## 存储模型

**K8s 存储是四层抽象，每一层都在解决上一层留下的问题：**

| 层 | 抽象 | 解决什么 | 留下的问题 |
|---|---|---|---|
| ① | 容器可写层 | — | 容器重建数据就没了 |
| ② | Volume | 数据挪到 Pod 层，容器重建不丢 | Pod 删除后数据仍会丢 |
| ③ | PV / PVC | 数据挪到集群层，跨 Pod 生命周期 | PV 要管理员手工建 |
| ④ | StorageClass | 动态供给，PVC 提交即自动创建 PV | — |

主线一句话：**每一层抽象，都是把数据往「更长寿」的地方挪。**

PV/PVC 的设计意图是**供需解耦**：管理员把已有存储池化成 PV（集群级），开发者按需提交 PVC（命名空间级），K8s 负责把两者匹配绑定。`StorageClass` 里的 `volumeBindingMode` 决定何时绑定（`Immediate` 立即 / `WaitForFirstConsumer` 等 Pod 调度后再绑），`allowVolumeExpansion` 决定 PVC 能否扩容。

详见 [PV / PVC 生命周期](./CKA/Week6/01-PV与PVC生命周期.md) 与 [StorageClass 与动态供给](./CKA/Week6/02-StorageClass与动态供给.md)。

## 配置与密钥

| | ConfigMap | Secret |
|---|---|---|
| 值形态 | 明文 | base64 编码 |
| 用途 | 非敏感配置 | 密码 / token / 证书 |
| 消费方式 | `envFrom`、`valueFrom`、volume 挂载 | 同左 |

两个必须记住的点：

- base64 是**编码不是加密**，一条命令就能还原，Secret 的真正防线是 RBAC（谁能 `get secret`）
- **环境变量注入不随对象更新**，要重启 Pod 才生效；**volume 挂载会热更新**（`subPath` 除外）

## 调度与资源

- `requests` 参与调度决策（节点必须有这么多空闲才可能被选中），`limits` 是运行时硬上限
- 由 requests/limits 的组合推出 QoS 等级：`Guaranteed`（都设且相等）> `Burstable`（只设部分）> `BestEffort`（都不设）；节点资源紧张时按这个顺序被驱逐
- 影响落点的其他手段：`nodeSelector`、`nodeAffinity`、`podAffinity`、`taints/tolerations`
